MosaiK8 · reference

The MosaiK8 numbers, next to GB Studio's

GB Studio Central's cheat sheet lists the limits of building for one console. This page puts the same figures next to ours for all nine consoles MosaiK8 targets. Start with the matrix; open a section below it when you want the detail behind a number.

One thing to know before reading. GB Studio counts nearly everything per scene, and lets you trade one budget against another inside a single console's memory: more background tiles means fewer sprite tiles. MosaiK8 counts per console, and mostly per world, because one project builds for nine machines and shares one tileset across every room.

So when a row below says different model, that is not a win or a loss. It means the two numbers are not measuring the same thing, and the note tells you what ours measures instead.

Reading the columns. Background tiles is the addressable table. On the Game Boy family the console font normally lives in it, leaving about 132 for your art, unless you switch the font out of video memory (see the Backgrounds section). Backgrounds  the tile budget, and the text trade-off 5 figures

GB Studio's four background rows are one budget seen four ways: it lets you trade background tiles against sprite tiles inside the Game Boy's 384 tiles of video memory. We do not trade. The split is fixed at 256 background plus 128 sprite, so these rows compare a sliding scale against a fixed one.

Background tileswith 96 sprite tiles free 128 256 background plus 128 sprite, fixed, with no trade to make ≠Different model The same 384 tiles, split the same way every time. You give up GB Studio's flexibility and gain never having to think about it.

Normally the console font sits in video memory alongside your tiles. Switch that option on and the font moves into the cartridge, with letters drawn on demand, so a room can use nearly the whole table. It costs about 1 KB of cartridge space and a brief pause on the first text box in a room. Available on the Game Boy family, Master System and Game Gear, where it more than pays for itself.
Background tilesoutside logo mode 256 256 on GB, GBC, Pocket, Mega Duck, NES, Lynx and PC Engine; 192 on Master System and Game Gear ◆Varies Level on seven consoles. The Master System and Game Gear can only address 192 background tiles: the space above that is where the hardware keeps the screen layout and the sprite list. Uploading past it corrupts the picture silently, so we make it a build error on those two.

The VM8 runtime  limits the GB Studio sheet has no row for 14 figures

VM8 is the event-script way of building: your logic is data, run by a small interpreter on the console. These numbers are the same on all nine consoles, set to fit the tightest one, so a single game runs everywhere without a "works on Game Boy, breaks on Lynx" class of bug. Where a number is deliberately copied from GB Studio, it says so. None of this applies if you write your game in code instead (see the next section).

It is one on PC Engine and three on Lynx. So the ratio is per room and per activity, and timing counted in script frames needs a per-console scale. An ordinary room now runs at the Game Boy's full rate when idle; the heaviest rooms do not, and that gap is the cost of drawing each character rather than anything trimming reaches.

Building without VM8  the code path, and what the studio still gives you overview

VM8 is one of two ways to build with MosaiK8. The other is to write the game yourself in mosaik, the language, and own src/main.mos outright. projects/game-slice is the worked example, and it runs on all nine consoles. Almost everything on this page still applies, because almost everything is the framework rather than the VM.

The short version. The matrix at the top of this page is hardware, so it applies to a code-written game exactly as it does to a VM8 one. The VM8 runtime table above is a runtime, so none of it applies: there is no 128-variable limit, no 8-script limit and no 8-actor pool. You keep your own state in ordinary variables and your own objects in ordinary arrays, bounded only by the console's memory and its sprite count.

What you get either way

CapabilityWhat it covers
Nine consoles, one source Game Boy, Game Boy Color, Analogue Pocket, Mega Duck, Master System, Game Gear, NES, Atari Lynx, PC Engine. Two compiler back ends underneath (one for the Game Boy family, Sega and NES machines, one for the Lynx and PC Engine), chosen for you.
The mosaik language Modules with imports and exports, variables and constants, structs, enums, functions (including ones you can store and pass around), if, while, loop, switch, break, continue, counted for loops, and the usual arithmetic, comparison, bitwise and logical operators. Not there yet: looping directly over an array, pointers, inline assembly, and the *= / /= / %= operators.
Per-console code A block guarded by the target console is resolved when you build, so only the matching branch ends up in the ROM. That is how one source file can do something different on the Lynx without costing the Game Boy anything.
The scene pipeline The Scene editor writes world.toml; Save and Transpile turns it into game code. Identical for both project styles: tilemaps, collision, doors, triggers, object placements, per-scene tilesets and sizes.
The asset pipeline Images become tiles automatically, with named sprite sheets, metasprites, the 16-colour tiers for sprites and backgrounds, and palettes that degrade honestly on machines that cannot show them.
Big-game support Cartridge banking, asset streaming, 2 x 2 tile compression and the shared paint routine all work regardless of how the logic is written, and they are the reason a world can be far larger than the console's memory.
Battery saves On the Game Boy family, 8 KB. Calling for it on a console without one is a clear build error rather than a silent no-op.
Ready-made building blocks Twelve engine modules: button edges, camera and scripted camera moves, cutscene sequencing, collision tests, scene helpers, dialogue, framed boxes, a HUD, menus, sideways and two-way scrolling for large levels, and an animation pool.
Genre kits Four, with templates: top-down, platformer, shoot-em-up and real-time combat.
The studio, mostly Scene editor, Inspector, project explorer, animation editor, palette designer, the pixel editor, video-memory layout, build settings and the budget meters, the console log, and the Game window with a real emulator plus memory and video-memory inspectors. Tiled map import and export and background image import work too.

What VM8 adds on top

These are the parts a code-written project does not get, because they exist to feed the interpreter. In exchange you write the equivalent yourself, in code, with no limits imposed by the runtime.

  • The visual event editor and the variables panel.
  • The dialogue library, with reusable named lines and values printed inside a sentence.
  • The timeline for cutscenes.
  • The HUD editor, which builds an overlay panel from labels, live values, gauges and icons.
  • The music tracker and the multi-channel music driver. A code-written game can still make sound through the simple tone functions, but the song format and the tracker belong to the VM8 path today.
  • The ready-made room wiring: doors, triggers, actor slots and per-scene-type behaviour, generated for you.

When to pick which

  • Choose VM8 if you want to build the game by assembling events, the way GB Studio works, and the runtime's limits are comfortable. Nearly all the worked samples take this path.
  • Choose code if you want something the event set does not cover, need more than the fixed pools, or care about speed: there is no interpreter in the way, so a code-written game has the whole frame to itself.
  • Both build to the same ROMs through the same pipeline, and both are edited in the same studio. The scene, art, palette and build tools do not change between them.

The three things this comparison actually shows.

1. We win on world size and lose on crowd size. Every scene-size row is ahead, and the streaming options move map data out of the console's memory altogether. The two rows where we are genuinely behind are the 8-actor default and the missing logo mode. The first is one setting; the second is real work nobody has done yet.

2. Colour is where nine consoles pay off. "3 colours for sprites, 4 for backgrounds" is a Game Boy fact. Three of our targets show 16-colour backgrounds as standard and a fourth can be switched to it, and two show 16-colour sprites, all from the same source art.

3. The Lynx is the console that sets the limits. Its 40 sprite tiles are our tightest constraint anywhere, its 160 x 102 screen is the shortest, and its single pool of memory for everything is why the VM8 numbers are what they are on all nine consoles rather than just on it.
